# Afflictio Roadmap

## Where the project is

Stages 1-6 are done (tags v0.1.0 through v0.6.0). The skeleton boots in QEMU on ARM64 with one script, `scripts/qemu-smoke.sh`, and the same scenario runs in CI: liinit mounts the filesystems and starts services, tiosessd brings up two autologin sessions on VT1 and VT2, the keyboard switches consoles through the HAL with Ctrl+Alt+Fn, session text really lands on the framebuffer through virtio-gpu, the supervisor restarts a killed daemon, and SIGTERM ends in a clean poweroff. The first device target is chosen (PinePhone): the pmOS artifact pipeline, the distribution rootfs with users and a manifest, flashable images with verification and the rootfs boot in QEMU run in CI in the `device` and `rootfs` jobs; the compositor draws windows on top of KMS in both scenarios, the Binder transport layer is covered by tests, and the modem AT layer runs over the second PL011 in QEMU against an EG25-G stub. What remains is the bring-up session to an installable phone distribution, and it is more honest to name the steps that separate the skeleton from a working system.

## Stage 1. Skeleton check in QEMU (done, v0.1.0)

Booting a kernel with initramfs in `qemu-system-aarch64 -machine virt` and confirming that init mounts the filesystems, starts services, reacts to signals and shuts the machine down. The test uses the `linux-virt` kernel from the Alpine repository: it is built for emulation and carries everything the virt machine needs. The kernel-from-source build script with the config fragment stays in scripts/build-kernel.sh for real devices. The check joined CI as the `qemu` job.

## Stage 2. Graphics and sessions (done, v0.2.0)

The terminal-only scenario reached an automated check. Text output: fbcon is built into the kernel, the `virtio-gpu` driver loads as a module from the kernel apk package; sessions print text on their VTs and the content of `/dev/fb0` compares byte by byte between the two consoles. Keyboard attachment: `virtio-keyboard-pci` in QEMU, the HAL reads evdev events, `ComboTracker` recognizes Ctrl+Alt+Fn, and a daemon thread rescans devices and sends switches into the main loop. VT switching by keyboard is verified with the QMP send-key command: the `SMOKE_SWITCH_VT1_OK` and `SMOKE_SWITCH_VT2_OK` markers confirm that both sessions switch by keyboard with no commands typed. Along the way a real bug got fixed: the session tty opened read-only, so all session output was silently lost.

## Stage 3. Devices through postmarketOS (done, v0.3.0)

The first target is chosen: PinePhone (Allwinner A64), the pmOS mainline kernel, SD card boot. `scripts/fetch-pm-kernel.sh` extracts the pmbootstrap pipeline artifacts without running pmbootstrap itself: the `linux-postmarketos-allwinner` 6.17.5 kernel, the PinePhone DTBs, 431 modules and the PinePhone U-Boot from the apk packages on the postmarketOS mirror; the kernel config comes out of the IKCONFIG stream embedded in the Image, so the check runs against the configuration of the kernel that was actually built. `scripts/check-kernel-config.sh` compares 16 requirements of our userspace against that config: every mandatory one holds (VT, fbcon, ext4, evdev among them), and the single warning `CONFIG_ANDROID_BINDERFS=n` moves into the stage 4 plan as a supplement to our fragment on top of the pmOS defconfig. `scripts/pack-device-bundle.sh` assembles the bundle: a boot directory (Image, DTB, extlinux.conf), three u-boot-sunxi-with-spl variants and rootfs.ext4 packed with mke2fs -d without root, with content verified through debugfs. All three steps run in CI in the `device` job. Flashing to hardware is described in devices/pinephone/README.md as a recipe for the bring-up session and has not been executed on a device yet.

## Stage 4. Compositor and Binder (done, v0.4.0)

The mainline graphics path is covered by a minimal compositor: the `tiocomp` crate with the `tiocompd` daemon writes the KMS/DRM layer on raw ioctls (two-phase `GETCONNECTOR`, `CREATE_DUMB`/`MAP_DUMB`/`mmap`, `ADDFB2`, `SETCRTC`, `PAGE_FLIP` with a fallback to a full modeset), composes a frame from a background, two animated windows and 5x7 font text, and flips buffers; in QEMU with virtio-gpu the smoke test records `SMOKE_KMS_FLIPS_OK` at 159 flips, and on exit the daemon hands the CRTC back to fbcon. The freedreno, panfrost and panthor drivers will plug into the same layer on real devices. Binder is covered by the transport crate `liobinder`: parcels (string16, flat_binder_object, offsets), the kernel buffer mmap, `BINDER_WRITE_READ` parsing both BR-command layouts, freeing buffers through `BC_FREE_BUFFER`, a draft `GET_SERVICE` request to servicemanager and the `binderctl probe` utility; the command codes are pinned by tests, and the servicemanager layout can only be verified against a real stack on the device. binderfs mounts through the new `[[mounts]]` section in init.toml (a failed mount is logged and does not break boot), the config fragment already carries `CONFIG_ANDROID_BINDERFS=y`, and the smoke test prints the honest `SMOKE_BINDERFS_ABSENT` marker on the linux-virt kernel that lacks Binder. What stays for hardware: libhybris for closed stacks (it needs vendor blobs) and verifying the servicemanager layout. One correction along the way: the PinePhone modem is driven by eg25-manager in pmOS over AT commands through USB-serial, not over Binder; the Binder path matters for vendor-RIL devices like the OnePlus 6, and the AT layer joins at the bring-up stage.

## Stage 5. Distribution build

Rootfs build scripts (a minimal busybox and coreutils set, Afflictio userspace packages), images for the first target, flashing documentation through fastboot and SD. Pieces proven in stages 1-3: musl binary builds, cpio packing, kernel modules inside the initramfs, boot composition with modules, pmOS artifacts and rootfs.ext4 through mke2fs -d. The stage ends with an image that flashes onto the PinePhone and boots to a terminal with autologin.

## Stage 6. The modem AT layer (done, v0.6.0)

The `lioat` crate covers the modem conversation without external dependencies: the `lioatd` daemon and the `modemctl` utility (30 tests, musl-aarch64 build). The AT channel is written on raw termios and poll: a command goes out as a frame with `\r`, the reply is collected line by line until the final `OK`/`ERROR`/`+CME ERROR`, echo is stripped, and partial lines plus replies of consecutive commands survive call boundaries in the channel buffer. The probe sequence is the standard 27.007 set: `ATE0`, `AT+CGMI`, `AT+CGMM`, `AT+CPIN?`, `AT+CSQ`, `AT+CREG?`; the replies yield the SIM state (READY/SIM PIN/SIM PUK), the signal level (21 maps to -71 dBm) and the network registration.

The transport is described in lioat.toml as a device list with fallback: on a real PinePhone it is `/dev/ttyUSB2` (the AT port of the EG25-G behind the `option` driver), in QEMU it is the second PL011 `/dev/ttyAMA1`; the daemon waits for the device to appear, never exits and never breaks the boot, and the re-probe interval and the reply timeout are configurable. Control follows the lioipc style: `modemctl status` returns a JSON snapshot through the daemon unix socket, `modemctl at CMD` sends an arbitrary command, and the protocol is pinned by tests.

The smoke in the `rootfs` job exercises the whole path: `scripts/modem-emu.py` runs an EG25-G stub (Quectel, READY, +CSQ: 21,99), a second QEMU `-serial` creates the second PL011 (`pl011@9040000` shows up in the DTB; on qemu builds without the second UART the check is honestly skipped), and lioatd prints `SMOKE_MODEM_AT_OK path=/dev/ttyAMA1 manufacturer=Quectel model=EG25-G pin=READY rssi=21`. The kernel requirement list grew to 19: `CONFIG_USB_SERIAL`, `CONFIG_USB_SERIAL_OPTION`, `CONFIG_USB_NET_QMI_WWAN` joined (=y|m, built as modules in the pmOS kernel), and the rootfs and the bundle now carry 7 binaries with lioatd and modemctl among them. What stays for hardware: a real EG25-G behind USB (port `/dev/ttyUSB2`), the qmi set for data, and checking the behavior when the USB device disappears.

## Open questions

- The first device choice is settled (PinePhone); when the target list grows, the comparison starts with the OnePlus 6, which has a mainline qcom-sdm845 kernel and wide pmOS support.
- A minimal compositor exists and is verified in QEMU (and inside the rootfs distribution); whether to grow it into a full one (input, application buffers) or take a ready one (weston, sway, labwc) will be decided at hardware bring-up.
- The PinePhone modem: the `lioat` AT layer is ready and verified in QEMU over the second PL011 against an EG25-G stub; at hardware bring-up it meets a real EG25-G through `/dev/ttyUSB2`, the qmi set for data joins there, and the liobinder Binder path stays for vendor-RIL devices like the OnePlus 6.
- The update model (A/B partitions versus full-ota) is chosen during stage 5.
